M7: Working together

What and why. So far you hand over a theorem and wait. But you often know something the model doesn't: "try induction", "that lemma is false", "use these three squares". This chapter makes the search a partner. A Session is a shared notebook between you and the search. You can write in it at any time: add a hint, suggest your own lemma, reject a lemma, pin an approach you like, pause, resume, or stop. The search reads it at checkpoints (before every round, plan and lemma). And when the search runs out of ideas, it doesn't quietly give up: it asks you a specific question ("I can't prove this step: ... Lean said: ..."), and your answer buys it another round.

Two things happening at once: threads

The search and your typing must run at the same time, so they run in two threads: two flows of work inside one program. That needs some care when both touch the same data. This chapter uses three standard tools from Python's library:

  • Lock: with self._lock: lets only one thread at a time inside that block, so the search never reads the hints list while you're halfway through adding to it.
  • Event: a flag threads can wait on. pause() clears it, resume() sets it, and the search's checkpoint() calls wait(), which simply blocks while the flag is cleared.
  • Queue: a thread-safe mailbox. ask() waits on queue.get(timeout=...) until answer() puts something in.

    Everything becomes planner hints. A suggested lemma becomes the hint "The user suggests this lemma ... (it must still be proved)", so your lemma can never skip Lean's check. A pin becomes "keep developing this approach". A rejection does two things: it tells the planner not to use the lemma, and uses_rejected drops any plan that uses it anyway, matched by name or by statement with spacing normalized.

    stop() also sets the running flag and puts None in the answer queue. A paused search, or one waiting for your answer, would otherwise never notice the stop. edit_statement stops the search with a reason; the caller (the website, in M9) starts a new search on the new statement.

    hints() returns list(self._hints), a copy, so the search can't be surprised by the list changing under it.

  2. Teach the search to use a session. Replace the whole file:

    {{file:mathfinder/search.py@m7}}

    What changed:

    • search takes session=None. Each round it plans with hints + session.hints(), so a hint you type mid-search is used from the next round. Plans that use a rejected lemma are dropped with the reason "uses X, which you rejected".
    • stop_reason() is called before every round and plan, and prove_plan checks before every lemma. That's where a pause waits and a stop ends the search.
    • The for loop over rounds became while True, with a counter r. When r reaches rounds, it builds a question with build_question, sends it as an ask_user event and waits. A real answer becomes a hint, and rounds += 1 extends the loop by one. That's why it couldn't stay a for loop over a fixed range. It asks at most MAX_QUESTIONS times, and only at depth 0 (sub-searches never ask).
    • build_question picks the first stuck lemma of the best plan and quotes Lean's error, so the question is specific enough to answer.

  4. Add the interactive mode to the command line. Replace the whole file:

    {{file:mathfinder/cli.py@m7}}

    What changed: new COMMANDS help text, handle_command, interactive_search, a --interactive flag, and printing for the new events (ask_user, user_answer, no_answer, stopped).

    handle_command uses str.partition(" ") to split "hint try x" into the command word and the rest. While a question is open, the whole line is your answer (except pause/resume/stop).

    interactive_search starts the search in a threading.Thread. daemon=True means the thread won't keep Python running after the main program ends. The main thread reads your typing, but input() would block forever even after the search finished. Instead, select.select([sys.stdin], [], [], 0.5) waits at most 0.5 seconds for a typed line, then loops round to check whether the search is still alive. An empty string from readline() means the input ended (Ctrl-D). The result comes back through box, a dictionary both threads can see.

Common errors

  • Your typing seems ignored: commands are read only between the search's steps, and a single Lean run can take 30 s. The [hint added: ...] line confirms it arrived; the hint is used from the next round.
  • A test hangs: a thread waits forever. Check that stop() sets the event and puts None in the queue.
  • KeyError: 'result' after Ctrl-C: the search thread was interrupted before finishing. Just run again.
