M12: The benchmark

What and why. A handful of hand-picked examples can make any system look good. A benchmark is a fixed set of problems you run the same way every time, so you can measure how good the system really is, and whether a change made it better or worse. Research provers are compared on miniF2F, a set of competition problems (AMC, AIME, IMO and similar) already written as Lean statements. Ours is a small set in that style: 20 problems across algebra, number theory, induction and inequalities, from "solve 3x + 2 = 11" to "if two primes sum to 9, their product is 14". Every benchmark run is also traced, so it produces training data for M13 too.

  1. Create the problem set, one JSON object per line.

    {{file:bench/problems.jsonl}}

    The statements are already formal, the way miniF2F gives them, so the benchmark measures the search, not the formalizer. Names like h₀ are just hypothesis labels (type h\0 or copy them). A few things to notice: (i : ℚ) in gauss_sum_formula turns each i into a rational number so / 2 is real division, and in seven_divides_power the ℕ subtraction 2 ^ (3 * n) - 1 is safe because 2³ⁿ ≥ 1.

  2. Create the benchmark runner.

    {{file:mathfinder/bench.py}}

    run_one runs the ordinary search (no optimizer, no explanation: we measure finding proofs) and records whether it was proved, how long it took, how (direct automation or a plan with k lemmas), how many proof attempts were made, and the proof's length. try/except Exception makes sure one crashing problem can't stop the other nineteen.

    results_table builds a Markdown table: a summary line, one row per problem, and a per-topic count. {proved / len(rows):.0%} formats a fraction as a whole percentage. sorted({...}) makes a set of topics (no duplicates) and sorts it.

  3. Add the bench command. Replace the whole file:

    {{file:mathfinder/cli.py}}

    What changed: the import of load_problems, results_table, run_bench, and a new sub-command bench with --rounds (default 2, so a hard problem can't run forever) and --only (nargs="*" takes any number of names).

  4. Create the tests.

    {{file:tests/test_bench.py}}

    The Lean test checks that all 20 statements type-check, in a single Lean run with sorry proofs. A typo in a benchmark statement would silently make a problem unprovable, so this matters.

  5. Let export find the benchmark's traces. Replace the whole file:

    {{file:mathfinder/traces.py}}

    What changed: export used runs_dir.glob("*/trace.jsonl"), which only looks one folder deep. Benchmark traces live two deep (runs/bench-<time>/<problem>/trace.jsonl), so after our first benchmark run export silently ignored all of them. rglob ("recursive glob") searches every sub-folder.

  6. Add a test for that. Replace the whole file:

    {{file:tests/test_traces.py}}

    What changed: one new test at the end, with a trace two folders deep.

  7. Run the tests:

    uv run pytest -q tests/test_bench.py tests/test_traces.py

  8. Try two problems first (a few minutes):

    uv run python -m mathfinder bench --only gcd_180_168 two_pow_ge

  9. Run the whole benchmark. It takes about an hour, so start it and let it run (the results table is printed at the end and saved in bench/results/):

    uv run python -m mathfinder bench | tee bench/last_run.log

    tee shows the output and saves a copy to a file.

Read it honestly. 8 of 20 fell to the hammer alone, and every other one was solved in the first planning round. That means this set is easy for the system: it never needed sub-searches, many repair rounds, or your help. It's a good regression test (a change that breaks it is clearly bad), but not a measure of hard-problem skill. The real next step is the actual miniF2F set, or your own harder problems added to problems.jsonl. Your times and "how" column will vary, since the model is creative.

Common errors

  • test_every_benchmark_statement_typechecks fails: a statement in problems.jsonl has a typo. The error names it.
  • json.decoder.JSONDecodeError: a line in problems.jsonl isn't valid JSON (watch the quotes and commas).
  • The benchmark is much slower than an hour: another Lean-heavy job is running at the same time (e.g. the full test suite). Run them one after the other.
