M2: The hammer (no AI needed)

What and why. Many small lemmas fall to a single automatic tactic. Asking an LLM costs seconds and money; one Lean run that tries a dozen tactics at once costs nothing. So the hammer always goes first. In the same Lean run it also asks plausible to test the statement on random values. If it finds values that make the statement false, the search drops that lemma immediately and tells the planner why.

The tactics we try

TacticGood at
norm_numarithmetic with concrete numbers: 2 ^ 10 = 1024
simprewriting with hundreds of known simplification facts: n + 0 = n
omegalinear facts about integers / naturals: n < m → n + 1 ≤ m
decidesmall statements Lean can just compute: Nat.Prime 97
linarith / nlinarithlinear / nonlinear inequalities over ordered fields such as ℝ
positivitygoals like 0 < x ^ 2 + 1
ring_nf, field_simpalgebraic identities, clearing denominators
aesop, tauto, simp_alllogic puzzles and "use the hypotheses" goals
norm_num <;> nlinarith<;> means "then run the next tactic on every goal that's left"
exact?searches all of Mathlib for one lemma that closes the goal

  3. Create the hammer.

    {{file:mathfinder/hammer.py}}

    One Lean run for everything: hammer builds one candidate per tactic plus one plausible candidate, and hands them all to check_decls from M1. The first tactic in the list that worked wins, and since the list goes from fast to slow, the proof we keep is a cheap one.

    Why less fuel (HAMMER_HEARTBEATS = 100_000): a tactic that is going to work almost always works quickly, and fifteen slow failures would make every hammer call slow.

    exact? prints Try this: [apply] exact Nat.le_of_dvd hb h. suggestion keeps just exact Nat.le_of_dvd hb h, so the saved proof is instant instead of re-running a library search. str.removeprefix removes a prefix only if it's there.

    plausible plugs random values into the statement. When it finds a failure, Lean reports an error containing Found a counter-example! and counterexample_text squeezes it into one line. It can only sample types it knows how to generate (like ℕ and ℤ). For ℝ it reports that it can't build a "testable" instance, which we record as testable = False. A missing counterexample means "not refuted", never "proved".

Checkpoint

Try the hammer by hand on a true and a false statement:

uv run python -c "
from mathfinder.hammer import hammer
print(hammer('(n : ℕ) (h : n > 3) : 2 * n < n * n'))
print(hammer('(n : ℕ) : n ^ 2 ≤ 2 * n + 3'))
"

Expected (the counterexample value can differ because the testing is random):

HammerResult(proved=True, tactic='nlinarith', proof='nlinarith', counterexample='', testable=True)
HammerResult(proved=False, tactic='', proof='', counterexample='n := 4; issue: 16 ≤ 11 does not hold', testable=True)

And the full suite:

uv run pytest -q

The time varies a lot (2–4 minutes) with how warm your disk cache is. The count, 25, should match.

Common errors

  • test_hammer_finds_counterexample... fails with proved=True, tactic='exact?', proof='exact mf_hammer_0 ...': your Decl.render still writes theorem. Use example (step 1).
  • unknown tactic 'plausible': your Mathlib is older than late 2024 (it used to be called slim_check). Recreate lean_env as in Chapter 0.
  • The hammer takes minutes: a cold disk cache. The second run is much faster.
