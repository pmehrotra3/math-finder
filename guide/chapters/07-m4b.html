M4b: The prover

What and why. The planner breaks a theorem into lemmas. The prover's job is to get one lemma proved, using the cheapest tool that works. It climbs a ladder: cache (proved this before? free), then the hammer (automatic tactics, no AI), then Claude (several proofs at once, all checked in one Lean run), then repair rounds: Claude sees its failed proofs together with Lean's exact error messages and fixes them. This feedback loop is the main reason pairing an LLM with Lean works: the model rarely gets a proof right the first time, but Lean says precisely what's wrong. If the hammer finds a counterexample, the lemma is refuted and we stop, because no amount of effort proves a false statement.

  2. Create the prover.

    {{file:mathfinder/prover.py@m4b}}

    The cache is a JSON file mapping a key to a proof. The key is the lemma statement plus the earlier lemmas it can see, because a proof like exact key a b only works when a lemma named key exists. " ".join(text.split()) collapses all whitespace, so two spellings that differ only in spaces share one entry. ensure_ascii=False keeps symbols like ℕ readable in the file instead of ℕ.

    preamble_for puts the earlier lemmas in front of the attempts: with their real proof if we have one, otherwise with sorry. Using an unproved earlier lemma is fine here, because each lemma gets proved on its own, and the final check (M4c) only accepts the theorem once every lemma has a real proof.

    build_prompt shows the lemma, what it means in words, the lemmas it may use, and on repair rounds each failed attempt next to Lean's error (cut to MAX_ERROR characters to keep the prompt small). parse_proofs never trusts the model: it drops non-strings, empty strings and anything containing sorry/admit/axiom, and removes a leading by (we add our own).

    try_proofs turns every proof into a candidate and checks them all in one Lean run. It returns the first one that works, or the list of (proof, error) pairs to feed the next repair round.

    prove_lemma is the ladder itself. for round_number in range(1 + REPAIR_ROUNDS) gives one first try plus two repair rounds. failures[:2] shows the model at most two failures, since more makes the prompt long without helping much. A stuck lemma keeps the most useful Lean error in feedback, so the planner can see why it got stuck.

  3. Create the tests.

    {{file:tests/test_prover.py@m4b}}

    autouse=True applies the temp_cache fixture to every test in the file automatically. tmp_path is a built-in pytest fixture: a fresh empty folder per test.

    scripted_model is a fake Claude that gives pre-written answers in order: first a wrong proof (simp), then the right one. That lets a free, repeatable test check the whole repair loop with real Lean: the first proof fails, the second prompt contains Lean's error, the second proof passes, and asking again hits the cache without calling the model. The refutation test gives the fake model no answers, so any model call fails the test. That proves false lemmas never cost an LLM call.

    The induction proof in GOOD is worth reading. induction n with splits into the case zero (empty sum = 0 = 0², simp) and succ k ih, where ih is the statement for k. Finset.sum_range_succ peels off the last term, ih replaces the rest with k ^ 2, and ring checks k² + (2k + 1) = (k + 1)².

  4. Run the fast tests, then the Lean tests (about a minute):

    uv run pytest -q -m "not lean and not llm"
uv run pytest -q tests/test_prover.py

  5. Let the real Claude prove a lemma the hammer can't (about 40 seconds):

    uv run pytest -q -m llm tests/test_prover.py

Checkpoint

uv run python -c "
from mathfinder.planner import Lemma
from mathfinder.prover import prove_lemma
lemma = prove_lemma(Lemma('odd_sum', '(n : ℕ) : ∑ i ∈ Finset.range n, (2 * i + 1) = n ^ 2', 'sum of the first n odd numbers is n^2'))
print(lemma.status, '|', lemma.feedback)
print(lemma.proof)
"

What we got (about 40 s: the hammer fails, then Claude's first batch works):

proved | LLM
induction n with
| zero => simp
| succ k ih =>
  rw [Finset.sum_range_succ, ih]
  ring

Common errors

  • stuck with unknown identifier 'Finset.sum_range_succ'-style errors every time: the model used an old (Lean 3 / old Mathlib) name. The repair rounds usually fix this. If not, it's a sign the lemma should be split smaller.
  • A test fails with the model was called more times than expected: the code asked Claude when it shouldn't have (for example, the hammer didn't run first).
  • Stale results after you change a lemma's meaning but not its text: delete cache/lemmas.json.
