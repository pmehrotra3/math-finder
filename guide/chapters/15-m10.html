M10: The website

What and why. Everything so far happens in a terminal. This chapter gives Math Finder a face: one web page that walks you through the whole story. (1) Type a theorem in LaTeX and see it typeset as you type. (2) Check and approve its Lean form (or edit it). (3) Watch the search live as a tree of plans and lemmas, colour-coded by status, with a chat panel next to it for hints and answers; click any lemma to hint about it, reject it, or pin its plan. (4) Read the result: the explanation with real maths typesetting, the verified Lean proof, and a few numbers about the search.

Three languages, one page

  • HTML (index.html) is the structure: which boxes and buttons exist. Each important element has an id, so the code can find it.
  • CSS (style.css) is the look. Colours are defined once as variables (--ok: #6fd39a) and used everywhere (var(--ok)). A class like .lemma.proved styles every lemma that is proved.
  • JavaScript (app.js) is the behaviour: it reacts to clicks, talks to the server, and redraws the tree when events arrive.

Two libraries are loaded from a CDN (a public file server), so the page needs an internet connection: KaTeX typesets $...$ maths, and marked turns the Markdown explanation into HTML.

    The four <section>s are the four steps. All but the first start with class="hidden", and the code removes that class when it's time to show them. defer on the scripts means "download now, run after the page is built", so app.js can safely look up elements by id.

  2. Create the look.

    {{file:web/style.css@m10}}

    display: grid; grid-template-columns: minmax(0, 3fr) minmax(0, 2fr) puts the tree and the chat side by side (60% / 40%), and the @media (max-width: 900px) rule stacks them on narrow screens. The lemma status symbols (○ ◐ ✓ ✗ …) come from CSS alone: .lemma.proved::before { content: "✓ " } inserts the symbol before the text, so the code only has to set the class.

  3. Create the behaviour.

    {{file:web/app.js@m10}}

    post() sends JSON to the server with fetch. In JavaScript, async/await work just like in Python: await fetch(...) waits for the reply without freezing the page. If the server answers with an error code, throw raises an exception, the JavaScript version of Python's raise.

    renderMarkdown solves a real clash: Markdown treats _ and \ specially, which would corrupt LaTeX like $a_1$. So it swaps each maths piece for a placeholder (@@MATH0@@), lets marked convert the Markdown, puts the maths back, and only then lets KaTeX draw it.

    Safety: text from the model or from you is inserted with textContent (always shown as plain text) or escaped with escapeHtml before it goes into innerHTML. That way a stray <b> in a lemma, or in a<b inside some maths, can't turn into real HTML.

    startWatching opens the WebSocket: new WebSocket("ws://.../ws/" + id), with ws.onmessage called for every event. handleEvent is one big switch on the event kind that updates state (the plans, the current plan, the open question, counters), and then renderTree redraws the tree from state. Keeping all data in one state object and redrawing from it is simpler than editing the page piece by piece. Events with depth > 0 come from a sub-search and go into the chat log, not the main tree.

    The chat box sends whatever you type as a hint, unless the search has asked a question, in which case it's sent as the answer. The search can't wait for both at once, so the page keeps track of which one is wanted.

    runDemo replays recorded events from demo_events.json when you open the page with #demo at the end of the address. It's how you can work on the page's look without waiting for Lean or the model.

    What changed: two imports (Path, StaticFiles), WEB_DIR, and the last line, app.mount("/", StaticFiles(directory=WEB_DIR, html=True)). That serves every file in web/, and html=True makes / give index.html. It must come after all the routes, because FastAPI tries routes in order and a mount at / matches everything.

Common errors

  • The page is unstyled, or maths shows as raw $...$: no internet, so the CDN files didn't load. Everything else still works.
  • {"detail":"Not Found"} at /: the app.mount(...) line is missing, or web/index.html isn't there.
  • API calls return HTML instead of JSON: the mount comes before the routes. Move it to the very end of app.py.
  • The tree never fills in: open the browser's developer console (⌥⌘J in Chrome). A red error there usually names the line in app.js.
  • #demo shows nothing: web/demo_events.json is missing. Run step 7.
