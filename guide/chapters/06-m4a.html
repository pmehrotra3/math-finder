M4a: The planner and the critic's first check

What and why. This is where the search starts. We don't ask Claude for a whole proof, which for anything non-trivial usually has one broken step somewhere. We ask for a plan: an idea in a sentence or two, a few small lemmas (helper facts), and a short main proof that combines them. In game terms the planner is the policy: it proposes moves. Before anyone spends effort proving the lemmas, the critic asks Lean one question: if all these lemmas were true, would the main proof work? We find out by writing each lemma with sorry as its proof ("pretend this is proved") and checking the main proof against them. A plan that fails this check is broken however well its lemmas get proved, and we know that after a single Lean run.

  1. Give each candidate an optional private context in the checker. Replace the whole file:

    What changed: Decl has a new field context: str = "", and render wraps the candidate in namespace name ... end name when there is a context. A Lean namespace is a name prefix: a lemma key written inside namespace plan_0 is really plan_0.key, so two plans can both call a lemma key in the same file without clashing. Everything stays inside the candidate's line range, so an error in one plan's lemmas counts against that plan only.

    {{file:tests/test_lean.py}}

    What changed: one new test, test_render_with_context_uses_its_own_namespace.

  3. Create the planner.

    {{file:mathfinder/planner.py}}

    Lemma and Plan are the records the whole search passes around. status starts as "open" and later becomes proved, refuted or stuck.

    SYSTEM is the standing instruction. It fixes the exact format we can feed straight into Lean: a lemma "statement" is what comes after theorem name, which is the same format Decl uses. It also asks for genuinely different plans, because two rewordings of one idea fail together.

    build_prompt adds the user's hints under a "highest priority" heading, and any feedback from earlier failed plans. This is the hook for working together (M7) and for revising plans (M4c).

    parse_plans never trusts the model's JSON. Each plan goes through try/except (KeyError, AttributeError, TypeError), which skips plans with missing fields or wrong types, and plans with invalid or duplicated lemma names are dropped. NAME_RE is a regular expression for a simple Lean name: a letter or underscore, then letters, digits, _ or '.

  4. Create the critic (just its first check for now).

    {{file:mathfinder/critic.py}}

    lemma_context turns a plan's lemmas into Lean theorems proved by sorry. check_skeletons makes one Decl per plan: the statement is the main theorem, the proof is the plan's main proof, and the context is its sorried lemmas. Then all plans are checked in one Lean run. The lemmas use sorry on purpose, so here we only count real errors, which is why the main proof is first scanned for sorry/admit/axiom as plain text. zip(plans, problems) walks the two lists side by side.

  5. Create the tests.

    {{file:tests/test_planner.py}}

    The Lean test checks four hand-written plans in one run: one that works, one citing a lemma that doesn't exist, one whose lemma statement doesn't type-check, and one whose lemma is too weak for the main proof. The llm test asks the real Claude for plans and checks that at least one fits together.

  6. Run the fast tests, then the Lean tests:

    uv run pytest -q -m "not lean and not llm"
uv run pytest -q

Checkpoint

Ask Claude for plans and let Lean judge them (about a minute):

uv run python -c "
from mathfinder.planner import propose_plans
from mathfinder.critic import check_skeletons
T = '(a b : ℝ) : a ^ 2 + b ^ 2 ≥ 2 * a * b'
plans = propose_plans(T, n=2)
for p, probs in zip(plans, check_skeletons(T, plans)):
    print('PLAN:', p.sketch)
    for l in p.lemmas: print('   lemma', l.name, ':', l.statement)
    print('   main:', p.main_proof)
    print('   skeleton OK' if not probs else '   PROBLEMS: ' + str(probs)[:300])
"

What we got (yours will be worded differently, since the model is creative):

PLAN: Use the nonnegativity of (a - b)^2 and close with nlinarith.
   main: nlinarith [sq_nonneg (a - b)]
   skeleton OK
PLAN: Prove a lemma that a^2 + b^2 - 2ab equals (a-b)^2, which is nonnegative, then conclude by linarith.
   lemma diff_eq_sq : (a b : ℝ) : a ^ 2 + b ^ 2 - 2 * a * b = (a - b) ^ 2
   lemma diff_nonneg : (a b : ℝ) : 0 ≤ a ^ 2 + b ^ 2 - 2 * a * b
   main: have h := diff_nonneg a b
linarith
   skeleton OK

"skeleton OK" doesn't mean proved yet: the lemmas are still sorried. Proving them is M4b.

Common errors

  • The planner returns []: every plan was malformed. Print llm.complete(SYSTEM, build_prompt(...)) to see the raw answer.
  • Every skeleton fails with unknown identifier for its own lemmas: your render puts the lemmas after the example, or outside the namespace.
  • LLMError: invalid JSON twice: the model wrapped JSON in prose with stray braces. It's rare; rerun.
