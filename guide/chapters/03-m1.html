M1: The Lean checker

What and why. Everything in Math Finder rests on one question: does Lean accept this proof? This chapter writes lean.py, which asks that question from Python. Starting Lean and loading Mathlib takes about 20 seconds, so we never check one proof at a time. We write many candidate theorems into one file, run Lean once, and use each message's line number to work out which theorem it belongs to. That batching is what makes search affordable.

Three Lean ideas you need

  • Theorem = statement + proof. theorem name (n : ℕ) : n + 0 = n := by simp: the part before := is the claim, and by simp is a tactic proof (a small program that builds the proof).
  • sorry means "trust me". Lean accepts it with a warning, so we must treat it as not proved.
  • Heartbeats are Lean's fuel counter. set_option maxHeartbeats 200000 in gives one theorem a budget, so a runaway tactic fails that theorem instead of hanging the whole file.

  2. Create the checker.

    {{file:mathfinder/lean.py@m1}}

    HEADER starts every generated file. set_option autoImplicit false matters a lot: without it, a typo like undefined_thing in a statement silently becomes a new variable, and a wrong statement could "prove" fine. open BigOperators Real Nat Topology lets us write π, ∑ and n ! without prefixes.

    @dataclass turns a class with type-annotated fields into a simple record (it writes __init__ for you). field(default_factory=list) gives each record its own empty list. A plain = [] would be shared between all records, a classic Python bug.

    run_lean writes the code to a uniquely named file (uuid4), runs lake env lean --json on it, and always deletes the file (try/finally). start_new_session=True puts Lean in its own process group, so on timeout os.killpg kills Lean and any child processes it started. The Semaphore is a counter that lets at most MAX_PARALLEL threads inside the with _slots: block at once, so we never run more than two Lean processes in parallel.

    check_decls is the batching trick. While building the file it records each theorem's first and last line (code.count("\n") + 1 is the line number the next text will start on). Each Lean message carries a line number, so we hand it to whichever theorem's range contains it. A theorem passes only if it got no error and no hasSorry warning.

    verify_final is the strict last check: the whole proof file plus #print axioms. A proof that sneaks in axiom cheat : False can prove anything, and this catches it, because only Lean's three standard axioms (propext, Classical.choice, Quot.sound) are allowed.

  3. Create the tests.

    {{file:tests/test_lean.py@m1}}

    A fixture (@pytest.fixture) is setup code that tests receive as an argument. scope="module" means it runs once for the whole file, so five tests share a single 25-second Lean run. The test test_batch_bad_statement_fails exists because of the autoImplicit bug described above.

  4. Run the fast tests first (no Lean, instant):

    uv run pytest -q -m "not lean" tests/test_lean.py

  5. Then run everything:

    uv run pytest -q

Common errors

  • test_batch_bad_statement_fails fails with simp made no progress: your HEADER is missing set_option autoImplicit false.
  • Everything fails with preamble: unknown module prefix: LEAN_DIR doesn't point at lean_env/, or the Mathlib cache is missing (Chapter 0, step 7).
  • Tests hang for minutes: Lean is compiling Mathlib instead of using the cache. Rerun cd lean_env && lake exe cache get.
  • test_run_lean_timeout_is_reported fails: on a very fast machine import Mathlib might finish in under 1 s. That's unlikely, but if it happens, it's harmless.
