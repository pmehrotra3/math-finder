M11: From a proof to a better proof

What and why. The search stops at the first proof Lean accepts, and that proof is often clumsy: three helper lemmas where one line would do, or a black-box nlinarith where a two-line argument would actually show why. Once we have one verified proof, we can afford to look for a better one. "Better" depends on what you want, so there are three metrics (scoring rules; lower is better). Each one combines counts taken from the Lean code: steps (tactic lines), lemmas (helpers besides main) and heavy (brute-force automation calls):

MetricScorePrefers
shortsteps + lemmasthe fewest lines
readablesteps + lemmas + 5 × heavyexplicit reasoning over black-box automation
few_lemmas10 × lemmas + stepsone self-contained proof

The optimizer asks the model for a few rewrites, checks them all in one Lean run, and keeps the cheapest only if it beats the original and passes the strict final check. The search budget is bounded (one model call, one batch, one final check), and the original proof is never lost.

    METRICS is a dictionary of lambda functions, so adding a new scoring rule is one line. proof_stats reads the assembled file: indented lines are tactic steps (theorem headers aren't indented), lines starting with theorem are lemmas plus main, and words from HEAVY are counted wherever they appear.

    Reusing parts: candidates are checked with check_decls (M1), cleaned with the prover's parse_proofs (M4b), assembled with assemble and verified with verify_final (M4c), exactly like a normal search result. sorted(scored) sorts the (cost, index, code, plan) tuples by cost first. The loop breaks as soon as a candidate isn't cheaper than the original, because nothing after it in sorted order can be.

  12. Optimize a proof you already have. This uses the one saved in M8 (use your own folder name):

    uv run python - <<'EOF'
from pathlib import Path
from mathfinder.lean import HEADER
from mathfinder.optimize import optimize
from mathfinder.planner import Plan
code = Path("runs/20261114-152642/proof.lean").read_text().removeprefix(HEADER)
T = "(x : ℝ) (hx : 0 < x) : x + 1 / x ≥ 2"
for metric in ("short", "readable"):
    r = optimize(T, code, Plan("original", [], ""), metric)
    print(f"\n== metric={metric} improved={r.improved} cost {r.original['cost']} -> {r.best['cost']}")
    print(r.lean_code)
EOF

Checkpoint

We started from the two-lemma proof of x + 1/x ≥ 2 (combine_frac + quad_ineq, 4 steps, 1 nlinarith). About 1½ minutes later:

== metric=short improved=True cost 6 -> 2
theorem main (x : ℝ) (hx : 0 < x) : x + 1 / x ≥ 2 := by
  have h : x * (1 / x) = 1 := by field_simp
  nlinarith [sq_nonneg (x - 1), h]

== metric=readable improved=True cost 11 -> 4
theorem main (x : ℝ) (hx : 0 < x) : x + 1 / x ≥ 2 := by
  have key : x + 1 / x - 2 = (x - 1) ^ 2 / x := by
    field_simp <;> ring
  rw [ge_iff_le, ← sub_nonneg, key]
  exact div_nonneg (sq_nonneg _) hx.le

Different metrics, different winners. short picked a compact nlinarith proof. readable picked the one that shows the real reason: x + 1/x − 2 = (x−1)²/x, and a square over a positive number is ≥ 0. It has no black-box automation.

On the website, with "readable" chosen, the chat says Looking for a better proof (readable, current cost 6)… and then either Found a better proof: cost a → b or Kept the first proof, and the result shows a proof cost tile.

Common errors

  • improved=False every time: that's allowed. The first proof may already be the best the model can find. Try another metric.
  • Fast tests take many seconds: some CLI test reaches the real optimizer. Add --no-optimize to it.
  • argument --metric: invalid choice: the names are short, readable, few_lemmas.
