M13: Training scaffolding

What and why. Since M8 every run has been recorded, and mathfinder export turns the records into datasets. This last chapter prepares the ground for training your own prover: a small open model that learns from the proofs Math Finder found (and from the mistakes it made). That is how systems like AlphaProof improve: search produces proofs, the proofs train the model, and the better model searches better. We build the two missing pieces and test them for real on a laptop. We don't run serious training: that needs a GPU, hours, and far more data than a few dozen runs produce.

Three kinds of training data

FileTeachesMethod
sft_chat.jsonl"here's a goal, write this proof"SFT, supervised fine-tuning: imitate good examples
dpo.jsonl"for this goal, this proof is better than that one"DPO, direct preference optimization: learn from pairs
value.jsonl"will this lemma get proved?"a classifier, a value model the search could use to try promising plans first

  1. Make training/ a package (so tests can import it).

    {{file:training/__init__.py}}

  2. Create the data preparation script.

    {{file:training/prepare.py}}

    Chat format. Modern models are trained on conversations: a list of {"role", "content"} messages (system, user, assistant). sft_rows builds one conversation per proved lemma, and the assistant's reply is the proof. The prompt looks like the one the prover uses in M4b, so a trained model would feel at home there. dpo_rows builds TRL's preference format: one prompt, a chosen reply and a rejected reply.

    The split by goal (split_of) is the important detail. If two proofs of the same lemma landed in train and test, the test would measure memory, not skill: that's a leak. So we hash the statement (SHA-256, a fingerprint that's always the same for the same text) and send about 10% of statements to test. int(digest, 16) % 100 turns the hexadecimal fingerprint into a number from 0 to 99.

  3. Create the fine-tuning script.

    {{file:training/finetune.py}}

    LoRA freezes the model and trains small extra matrices next to it. Instead of updating billions of numbers, you update a few million, which fits on one GPU, and the result is a small adapter file (19 MB for the tiny model). target_modules="all-linear" puts adapters next to every linear layer.

    SFTConfig holds the training settings. gradient_accumulation_steps=8 adds up 8 small steps before updating, which behaves like a batch of 8 while only using the memory of 1. max_steps overrides the epochs, which is handy for smoke tests. The heavy libraries (torch, transformers, datasets, peft, trl) are imported inside train(), so --dry-run and the tests work without installing them.

  4. Never commit trained models. Replace the whole file:

    {{file:.gitignore}}

    What changed: the last line, models/.

  5. Create the tests.

    {{file:tests/test_training.py}}

    test_prepare_keeps_each_goal_on_one_side writes two proofs for each of 60 goals and checks no goal appears in both train and test, which is exactly the leak the split exists to prevent.

  6. Build the datasets from all your runs, and check them:

    uv run python -m mathfinder export
uv run python training/prepare.py
uv run python training/finetune.py --dry-run

  7. Optional: a real 2-step training run on a tiny model, on your CPU (about a minute; downloads ~300 MB of libraries and model the first time, into a temporary environment, so your project stays light):

    uv run --with torch --with transformers --with datasets --with peft --with trl \
    python training/finetune.py --base-model HuggingFaceTB/SmolLM2-135M-Instruct --max-steps 2 --out models/smoke-test

    uv run --with X runs the command with extra packages available just for that run.

Common errors

  • no training examples: run mathfinder export and training/prepare.py first. Only lemma-level proofs become SFT examples, so runs proved by direct automation contribute none.
  • Cannot use chat template functions ... no template: the base model has no chat template. Use an "-Instruct" or "-Chat" model.
  • Out of memory on a real model: lower --lora-rank, use a smaller model, or train on a GPU machine.
